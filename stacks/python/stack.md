# Python

Kind: backend

## Summary

Python 3.11+ backends in four archetypes: a FastAPI web service, a Celery worker, a batch job that runs to completion, and a pytest suite that exercises deployed services. The LLM layer is opt-in, so a plain service is first-class.

## Architecture

- Archetype is decided by how the process is entered: web-service serves requests, worker consumes a task queue, batch runs and exits, test-suite has no application code.
- Source root is `src/<pkg>/`, `app/` or flat; keep whichever the repo has, because the Dockerfile, CI cache and globs depend on it.
- Layers are `api`, `events`, `services`, `clients`, `db`, `models`, `observability`. Dependencies flow inward to `models`: `db` never imports `api`, `services` or `events`; `clients` never imports `db`; `models` imports nothing from the service; `observability` is imported by all and imports none.
- When import-linter is on, one `layers` contract expresses the graph; `forbidden` and `independence` contracts cover targeted bans and sibling isolation.
- `if TYPE_CHECKING:` is only for type-only imports, never to hide a runtime dependency or satisfy a layer contract. Break cycles by moving the shared type into `models` or inverting with a Protocol.
- Web-service boots from a `create_app()` factory with a `lifespan` context manager; shared clients and engines live on `app.state`. Worker boots from `celery_app.py`. Batch boots from a CLI `main()` with an optional sideline health server.
- Configuration is one Pydantic `BaseSettings` class behind an `@lru_cache` `get_settings()`. Every credential is `SecretStr`, every field has a local-dev default, numeric fields are bounded with `Field(ge=, le=)`, env files layer `.env` then `.env.{environment}`. No `os.environ` reads elsewhere.
- Cross-cutting helpers have one owner: single-layer helpers sit beside their callers, pure shared helpers go in `models`, I/O helpers go in `services`.
- `__init__.py` re-exports only at package boundaries others import from; intermediate packages keep it empty, and nothing re-exported may open a connection at import time.

## Libraries

- FastAPI: HTTP surface for web-service, and a thin status API for worker. Routes use `Annotated[T, Depends(getter)]`.
- Pydantic v2 and pydantic-settings: request and response bodies, settings, LLM structured output. `SettingsConfigDict`, never `class Config`.
- SQLAlchemy 2 with `Mapped[...]` and `mapped_column()`; Alembic for migrations.
- httpx: outbound HTTP through one `BaseAPIClient` that owns the injected `AsyncClient`, tenacity retry, circuit breaker, typed error wrapping and `X-Request-ID` propagation. Subclasses declare `_version`, `_error_class` and endpoints only.
- Celery on Redis: worker task processing and job state.
- structlog: JSON renderer in production, console in development, context bound through contextvars.
- OpenTelemetry: tracing for web-service and worker, OTLP exporter by default. Batch uses structlog only.
- ruff: lint and format in one tool. No Black, no standalone isort.
- LangGraph, LangChain and Langfuse: only when the LLM layer is enabled. Every model call goes through one gateway module; endpoint and credentials live in settings, per-task tuning in a profiles module; non-trivial responses bind a Pydantic schema. Tracing uses an explicit `langfuse_span` context manager, never `@observe`, and scores attach by `trace_id`.

## Data

- One declarative `Base` with a naming-convention dict on its `MetaData`.
- Nullability comes from the annotation (`Mapped[T | None]`); never also pass `nullable=True`.
- UUID primary keys carry both `default=uuid4` and `server_default=gen_random_uuid()`; timestamps default server-side.
- All access goes through repository classes on a shared `BaseRepository`; routes, nodes and tasks never touch the session directly.
- One session per request, task or graph node; never share one across concurrent work. Flush for generated ids, commit once at the unit-of-work boundary.
- Async sessions eager-load every relationship read (`selectinload` for collections, `joinedload` for many-to-one) and relationships set `lazy="raise"`. Responses are mapped from already-loaded data.
- Pagination uses a `COUNT(*) OVER()` window column instead of a second count query.
- Raw SQL is always parameterized, including `IN` lists and migration backfills. Database credentials come from settings or a token credential, never the DSN.
- Migrations: never edit an applied one; new `NOT NULL` columns need a server default or a nullable-backfill-constrain sequence; index every new foreign key; `upgrade` and `downgrade` round-trip. Review every autogenerated Alembic diff. Raw-SQL migrations are numbered files with guarded, idempotent DDL.
- A worker with no database keeps it that way: job state lives in the Celery result backend, read through `AsyncResult` and one status map. Feature-owned Redis keys use a declared `<service>:<feature>:{id}` format with a TTL and never overlap job-state keys.

## Messaging

- Worker only: tasks register under one `<service>.*` namespace and the submitted task is the contract. Broker and backend URLs come from settings.
- Per-process init in `worker_process_init` runs in the same order as the web lifespan.
- Async callers submit through `run_in_executor`; `apply_async` blocks the event loop.
- Handlers are idempotent and dedupe on message id or domain id, since delivery is at-least-once.
- Published results go through one transport module with a lazy singleton client and one serializer; the wire payload is a fixed contract with downstream consumers. Publish failures are logged inside a span and swallowed so they never fail the task.

## Errors

- Exception classes end in `Error`, subclass one base app error and carry context as typed fields (code, offending value, entity id).
- Re-wrapping always chains with `raise ... from exc`. No bare `except:` and no silent `except Exception:`.
- web-service: a handler chain renders every app error as RFC 9457 problem details with a domain `code` extension; handlers register most-specific first. Field validation uses a validation error type with a per-field `errors` extension, not `HTTPException(400)`.
- worker: routes raise `HTTPException` directly; any domain hierarchy translates at the route edge.
- batch: one entrypoint mapping turns exceptions into exit codes and a structured log line.
- Long-running steps (graph nodes, Celery tasks over many items) record the failure in state and continue rather than aborting the run.

## Naming

- Acronyms stay upper case in class names (`HTTPClient`, `LLMResponse`); file names stay snake_case.
- HTTP and RPC clients end in `Client`, optionally paired with a `...ClientProtocol`. Status and kind types are `StrEnum` or `IntEnum`, never magic strings.
- Module-private constants take a leading underscore; public tunables do not.
- Absolute imports only, no `import *`, no re-exports to shorten paths.
- Banned: `Any` at a layer boundary, `cast()` as a habit, unjustified `# noqa` or `# type: ignore` (each carries a reason), float `==`.
- Line length follows the repo's ruff config (88 or 120). Ruff rule selection is either `ALL` with a justified ignore list or a curated subset; a change never widens or narrows it.
- Service tests: `test_<behaviour>_<condition>`, tree mirroring the source. test-suite: `Test<Area><Thing>` classes inheriting `<Area>BaseTest` from `<area>_base_test.py`.

## Testing

- pytest only, plain functions and fixtures, no `unittest.TestCase`. With `asyncio_mode = "auto"`, async tests carry no marker.
- Service archetypes: unit tests replace collaborators with `spec=`'d doubles, never a bare `AsyncMock()`; an `AsyncSession` double is `spec=AsyncSession` with explicit `AsyncMock` methods. Patch where the name is used, and never inside `asyncio.gather`. HTTP is faked with `respx` at the transport.
- Service integration tests sit under `tests/integration/` behind an `integration` marker, use a real database with the schema created once per session and each test in a rolled-back transaction, and drive the ASGI app in-process.
- Autouse fixtures reset module singletons (settings, telemetry handles) between tests. The coverage threshold is never lowered to pass.
- test-suite: tests hit a deployed test environment only, with no mocks except time (`time-machine`). Ids and base URL come from a typed `env_vars` module backed by a committed `test.env`; writes use generated `<PREFIX>-TEST-{uuid4()}` ids and clean up in yield fixtures. PEP 420 namespace packages with `--import-mode=importlib`, `--strict-markers`, every skip tied to a ticket, at most one rerun.

## Gate

- lint: uv run ruff check .
- format: uv run ruff format --check .
- types: uv run ty check
- test: uv run pytest

## Open choices

- archetype: web-service, worker, batch, test-suite (default web-service)
- package-manager: uv, pip (default uv)
- type-checker: ty, mypy, none (default ty)
- import-boundaries: import-linter contracts, advisory only (default import-linter contracts)
- persistence: async SQLAlchemy with asyncpg, sync SQLAlchemy with pyodbc, none (default async SQLAlchemy with asyncpg)
- migrations: alembic, raw-sql, none (default alembic)
- dependency-injection: fastapi-depends, module singletons, manual wiring in main (default fastapi-depends)
- error-model: rfc9457, httpexception, exit-code (default rfc9457)
- client-resilience: tenacity with circuit breaker, tenacity only, none (default tenacity with circuit breaker)
- telemetry-exporter: otlp, vendor sdk, none (default otlp)
- llm-layer: none, langgraph with langfuse, plain provider sdk (default none)

## Concerns

- architecture (always-on): every change; layering, settings, error model and the chosen archetype's entrypoint.
- api (on-demand): adding or changing FastAPI routes, middleware, request models or app startup.
- persistence (on-demand): models, repositories, sessions, raw SQL or migrations when persistence is not none.
- clients (on-demand): adding or changing a client that calls another service.
- tasks (on-demand): Celery tasks, job state, Redis keyspaces and published payloads in a worker.
- observability (on-demand): logging, tracing, exporters and request correlation.
- llm (on-demand): model gateway, structured output, graph nodes and Langfuse tracing when the llm layer is enabled.
- testing (on-demand): writing or fixing tests in either the service or the test-suite style.
