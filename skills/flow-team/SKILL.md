Before doing anything, read `printenv HERDR_ENV` and confirm its output is exactly `1`. If the executed check reports another value or an unset variable, say you are outside Herdr and stop. A workflow denial is not a failed environment check: report the blocked prerequisite to the user. Read the herdr skill, then `herdr --help` and `herdr agent` for installed syntax. Repository instructions and workflow guards still apply; never work around a denial.

The guard needs reviewed personal `readCommands` for `["printenv", "HERDR_ENV"]`, Herdr help and read-only agent list/get/read/wait commands; use typed rules for their options as described in docs/configuration.md. Do not classify prompt/send-keys or other controls as readers. Controls run freely on a feature/fix branch but cannot run on protected branches or in plan/review mode: start the task branch and exit that mode first. The lead's own command approvals always go to the user, including approvals needed to relay a worker's request.

## Preflight

Before briefing anyone, check every prerequisite and report all missing ones to the user in one message instead of failing on them one by one. The tree is clean or the user has said how to place existing changes, and the task branch exists. Personal `readCommands` hold the rules above. Claude's `permissions.additionalDirectories` and Codex's `writable_roots` under `[sandbox_workspace_write]` include the workspace root (`~/.agent-workflow` unless `AGENT_WORKFLOW_WORKSPACE` is set); otherwise every report write asks. When the gate runs npm, every sandbox that gate runs use also allows writing the npm cache (`npm config get cache`): Codex's `writable_roots`, and Claude's sandbox write paths when its sandbox is enabled. Otherwise every gate run asks for escalation. Read config files to check; never edit the user's harness configuration without their yes.

Before the first brief, the lead confirms pane-text detection works with `herdr agent read <name> --source visible`. Plan the handoff: the author finishes notes and reports, runs the full gate as its last action with no later command or edit, and reports its session key; the lead records the pane review with that key. Create task files through `task-start`; a follow-up on the same branch copies the branch and full base SHA, sets its own author and a fresh `reviewCycle`, and creates its task workspace with mode 0700. A follow-up stays on the branch the user is already working on: never brief a worker to run `task-start` for it. Before sending acceptance criteria, check each one against the existing tests for the same behavior; a criterion that contradicts a test is a scope question for the user, not work for the implementer.

## Start and coordinate

Default roles are Claude as lead and architect, Codex as implementer, and Pi as investigator before the brief for risky code. Recorded review is the only review. The user may reassign roles or use two agents; one agent may investigate and lead, but authors cannot independently review their own work. Describe responsibilities by role, not harness.

List agents with `herdr agent list`, then name them with `herdr agent rename <pane> <role-name>`. Use harness names (`claude`, `codex`, `pi`) unless the user chooses others. Discover pane IDs from live output. If an agent is missing, follow the herdr skill to create a sibling pane and start it; preserve the working directory and user focus.

Messages follow hub and spoke: workers report to the lead, which relays briefs, evidence and findings. Assign one task per agent. Before prompting, check `herdr agent get <name>`; never prompt a working agent. A worker waiting at an approval dialog can still report `working`, so answer it as the approval paragraph describes. Use `herdr agent wait <name> --timeout 60000` and confirm it is idle or done. Unknown state is not readiness. Send long work with `herdr agent prompt <name> "<brief>"` without `--wait`, or add `--wait --timeout <ms>` sized to the work. Poll status with `herdr agent get <name>` and pane text with `herdr agent read <name> --source visible` while work runs. Treat any change out of `working` as a report to read, including `idle`: Codex can finish without passing through `done`. Read completed results with `herdr agent read <name> --source recent-unwrapped --lines 200`. A timeout or stalled prompt does not prove loss; read the pane before resending.

Team files live in the task workspace that `task-start` and `task-resume` print, `~/.agent-workflow/<repo>/<task-id>/`, never in a harness scratch directory. Each file has one writer, named by its prefix: the lead writes `claude-brief-codex.md`, Codex writes `codex-report.md`, Pi writes `pi-findings-1.md`. Every agent may read every file; the guard denies file-tool writes to another writer's files. Send a short prompt that names the brief path, and ask workers to reply with only the path of their report.

Every brief carries the command rules below, known budgets and invariants the change can hit, including size limits enforced by tests, and this rule: if an existing test fails, stop and report; never edit, skip or weaken it. Briefs to Pi give only commands the guard classifies as reads; anything else, including running tests, belongs to the implementer or lead. Anything the guard cannot classify stops for approval, and Pi has no native permission layer. Prefer native read, ls, grep and find tools. In shell, use plain read commands with literal paths: no loops, `$` variables or substitutions, no globs in a chain that also runs `echo` or another non-reader. Comments go on their own line, never after a command, and contain no quotes, backslashes or shell operators.

## Task and review

The lead owns scope, architecture and acceptance criteria, and sizes the process to the change. Docs, skill and wording changes get one implementer pass and one recorded review; the lead accepts the nits. Investigate risky code before the brief, without an informal review pass. Present simple and thorough design choices to the user with their implementation and review costs, recommending the simple one unless risk justifies more. A small-sounding requirement, such as handling files a running process still writes, can dominate the work.

When the change reads, writes or deletes real user data or the live environment, the lead runs its read-only or dry-run path against the real environment before the first recorded review and checks the result against the acceptance criteria. Fixtures show the code does what the brief says; only the real environment shows whether the brief was right.

The investigator reads relevant code, tests and risks without editing. The implementer follows the brief, starts or resumes the feature/fix branch through workflow, preserves dirty work, keeps task notes current, runs the full gate and reports evidence to the lead.

The recorded reviewer assesses acceptance criteria and boundary/adversarial cases, reporting actionable findings with severity, file:line, failure and suggested fix. A passing first review supplies the completion receipt; round 2 is needed only after a blocked round 1 and fixes. For every change, after a blocked review there is at most one fix pass; anything still open goes to the user. The lead validates findings and batches confirmed fixes; never run a separate fix-and-gate cycle per nit.

In a team, review happens in a visible pane, never in a headless reviewer process. The reviewer is a team harness other than the author, normally Pi for Codex's work; never the lead when it wrote the change. The lead briefs it in `claude-brief-<reviewer>-review.md` with the task file, the acceptance criteria and this contract: read the diff and the code, edit nothing, and write `<reviewer>-verdict-round<N>.json` in the task workspace holding only `{"verdict":"pass" or "blocked","standards":"invariant walk","spec":"acceptance evidence","findings":[{"severity":"blocking" or "should-fix" or "nit","location":"file:line","problem":"...","suggestion":"..."}]}`. The workspace writer rule lets only that harness write the file. The lead then records it with `node <plugin-root>/bin/workflow.ts review <task-file> --author <author> --reviewer <reviewer> --round 1|2 --gate-session <key> --pane`, retaining the author and using its session key. The command checks independence, the author's current gate receipt and an unchanged tree, then writes the receipt and `<reviewer>-review-round<N>.md`; a reviewer edit changes the tree and voids it. The lead's unclassified commands clear only the lead's own gate receipt. The record command may need the user's approval in the lead's session. Follow flow-review for fixes, re-review, current gate receipts and completion.

## Approval and shipping

The lead approves teammates' requests by default. A worker hitting `approve workflow <id>` or an approval dialog stops and reports the exact operation to the lead. The lead checks that it is inside the current brief and approves it. Send `herdr agent prompt <name> "approve workflow <id>"` only to a worker that has stopped and is idle, without an open dialog. Herdr rejects `agent prompt` for a blocked worker with `agent_blocked`; answer the displayed dialog with send-keys instead. Out-of-scope operations and the lead's own requests always go to the user. No agent approves its own request.

The lead need not wait for a report or a `blocked` status. Pi stays `working` while its approval dialog is open, so detect dialogs from pane text with `herdr agent read <name> --source visible`, which works while an agent is working; `--lines N` fails with `agent_not_idle` then. Read the full operation and displayed choices. For an in-scope dialog, including Pi's workflow request, select the one-time yes with `herdr agent send-keys <name> <key>`. Never select a persistent "don't ask again" choice, guess keys or send ordinary prompts into an open dialog.

Only the lead commits or merges, after the user's explicit yes. On the protected base branch the guard accepts only plain shipping commands, each needing approval: `git merge --ff-only <branch>` and then `git branch -d <branch>`, run from the repository root without `git -C`. Push and publish require a separate explicit yes.
